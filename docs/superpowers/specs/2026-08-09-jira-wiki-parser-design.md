**Date:** 2026-08-09
**Project:** tg_poker_planing — Planning Poker (Telegram Bot + Web Interface)

## Context

Описание задачи из Jira отображается в веб-интерфейсе через `parseJiraDescription`
(`web/static/adf-parser.js`). Функция разбирает два формата: ADF — JSON-дерево,
которое отдаёт Jira Cloud REST v3, и wiki-разметку — текстовую, которую отдаёт
Jira Server/Data Center и Cloud REST v2.

Владелец использует **Jira Server/Data Center**. Браузерное расширение ходит в
`/rest/api/2` (`browser-extension/background.js:89`), поэтому описание всегда
приходит текстовой wiki-разметкой. То есть работает именно та ветка парсера,
которая сломана, а исправная ADF-ветка на практике не задействуется.

### Что именно сломано

Проверено прогоном `parseJiraDescription` в браузере на текущем `main`:

| Ввод | Текущий результат |
|---|---|
| `Поле user_name_id пустое` | `Поле user<em>name</em>id пустое` |
| `[Дока\|https://wiki.corp/api_v2_spec]` | `href="https://wiki.corp/api&lt;em&gt;v2&lt;/em&gt;spec"` — ссылка ведёт в никуда |
| `Нужно C++ и Java+Kotlin` | `Нужно C<u>+ и Java</u>Kotlin` |
| `{panel:title=Важно}Текст{panel}` | `<div class="jira<s>panel jira</s>panel<s>info">` |
| `# раз` / `# два` | `<br><ol><br><li><br></ol><br>раз</li>` |
| `* первый` / `* второй` | список верный, но между `<li>` вставлены `<br>` |
| `\|\|Имя\|\|Тип\|\|` + `\|a\|b\|` | строки данных не отрисованы, заголовок вышел как `<td>` |
| `{code}...https://...{code}` | внутри блока кода URL стал ссылкой, переводы строк — `<br>` |

### Корень

`parseWikiMarkup` — цепочка из двух десятков `String.replace` по одной строке.
Каждое следующее правило работает по HTML, который произвели предыдущие. Правила
для `-зачёркнутого-`, `_курсива_` и `+подчёркивания+` съедают дефисы в именах
CSS-классов, подчёркивания в идентификаторах и адресах, плюсы в тексте. Плюс к
тому весь текст экранируется в самом начале, поэтому вставленные позже теги
попадают в уже экранированную строку — отсюда `&lt;em&gt;` внутри `href`.

Собственные тесты этого не ловят: `tests/e2e/fixtures/wiki-samples.ts` содержит
семь однострочных примеров вида `This is *bold* text`, и все они проходят.
Playwright в репозитории не установлен, то есть даже эти семь не запускаются.

## Цели

1. Wiki-разметка отображается корректно в повседневных случаях — все восемь
   поломок выше исчезают.
2. Ошибка такого класса больше не возникает по построению: правило не может
   испортить результат другого правила.
3. Парсер покрыт автотестами, которые запускаются без установки зависимостей.

## Вне scope

- **ADF-ветка.** Логика разбора работает корректно и не меняется. В ней меняются
  ровно две вещи: она остаётся в `adf-parser.js` рядом с точкой входа (см. «Файлы»),
  и её `escapeHtml` переводится на ту же чистую функцию, что и в wiki-парсере.
  Нынешняя реализация через `document.createElement` не даёт импортировать файл в
  Node — без этой замены тесты диспетчера не запустить, — и вдобавок не экранирует
  кавычки, хотя результат подставляется в том числе в значения атрибутов.
- **Переход на `/rest/api/3`.** На Server/DC такого API нет.
- **`formatTaskText`** (`web/static/script.js:1803`) — отдельная функция для
  описаний не из Jira, обычный текст плюс ссылки. Не трогаем.
- **Переделка браузерного расширения.** Известные проблемы безопасности
  расширения — отдельная работа.
- **Макросы Jira** за пределами перечисленных в «Поддерживаемая разметка».

## Файлы

```
web/static/
├── wiki-parser.js   ← новый: вся wiki-разметка
├── adf-parser.js    ← только ADF + точка входа parseJiraDescription
└── script.js        ← не меняется
```

Сейчас `adf-parser.js` держит оба формата и занимает 262 строки. После
переписывания wiki-часть заметно вырастет, и вместе вышло бы за 450 строк в одном
файле. Разделение даёт каждому файлу одну ответственность и позволяет
импортировать их в тестах по отдельности.

**Точка входа** остаётся `window.parseJiraDescription` в `adf-parser.js` с
неизменным контрактом: объект с `type === 'doc'` разбирается как ADF, строка — как
wiki, всё прочее приводится к экранированной строке. Диспетчер вызывает
`parseJiraWiki`, а если тот не загружен — возвращает экранированный текст, а не
падает.

**Подключение** в `web/templates/index.html`: `wiki-parser.js` перед
`adf-parser.js`, обе строки перед `script.js`.

**Двойной экспорт.** Каждый файл заканчивается хвостом вида

```js
if (typeof module !== 'undefined' && module.exports) { module.exports = { parseJiraWiki }; }
if (typeof window !== 'undefined') { window.parseJiraWiki = parseJiraWiki; }
```

Так файл остаётся обычным `<script>` для страницы и импортируется в Node без
сборщика. В корне репозитория нет `package.json`, поэтому Node трактует `.js` как
CommonJS и `require` работает.

## Архитектура парсера

Три последовательных шага вместо цепочки замен. Ключевое свойство: **HTML
появляется только на последнем шаге**, поэтому ни одно правило не может встретить
и испортить результат другого.

### Шаг 1 — блочный разбор

Построчный проход по исходному тексту, на выходе — плоский список блоков. Каждый
блок несёт тип и либо сырой текст, либо вложенные блоки.

| Разметка | Блок | Содержимое разбирается дальше? |
|---|---|---|
| `{code}` … `{code}`, `{code:java}` … | `code` | **Нет.** Текст сохраняется дословно |
| `{noformat}` … `{noformat}` | `code` | **Нет** |
| `{quote}` … `{quote}` | `quote` | Да, как блоки |
| `{panel}` … `{panel}`, `{panel:title=X}` … | `panel` | Да, как блоки |
| `h1.` … `h6.` | `heading` | Да, инлайново |
| строка начинается с `\|` | `table` | Да, инлайново в каждой ячейке |
| строка начинается с `*`, `-`, `#` и пробела | `list` | Да, инлайново в каждом пункте |
| `----` | `rule` | — |
| пустая строка | разделитель абзацев | — |
| прочее | `paragraph` | Да, инлайново |

Блоки кода распознаются первыми и поглощают строки до закрывающего маркера, что и
делает их содержимое неприкосновенным: остальные шаги внутрь не заглядывают.
Незакрытый `{code}` поглощает текст до конца ввода.

**Таблицы.** Заголовочная строка — ячейки между `||`, обычная — между `|`.
Соседние строки собираются в одну таблицу; ячейки заголовочной строки выводятся
как `<th>`, обычной — как `<td>`.

**Списки.** Глубина вложенности равна длине серии маркеров (`*` — первый уровень,
`**` — второй). Тип берётся по первому символу серии: `#` — нумерованный, `*` и
`-` — маркированный. Смешанные серии вроде `*#` Jira допускает; здесь тип
определяется по первому символу, что для практических описаний достаточно.

### Шаг 2 — инлайновый разбор

Применяется к тексту внутри блоков и никогда к сгенерированному HTML. Сканер идёт
слева направо и на выходе даёт список инлайновых узлов.

Встретив открывающий маркер непрозрачного фрагмента, сканер забирает фрагмент
целиком и внутрь не заходит:

- `{{моноширинный}}` — содержимое становится текстом узла `code`
- `[текст|адрес]`, `[адрес]` — метка разбирается инлайново, **адрес остаётся
  непрозрачным**. Именно это чинит битые ссылки

Остальные маркеры: `*жирный*`, `_курсив_`, `-зачёркнутый-`, `+подчёркнутый+`,
`^верхний^`, `~нижний~`, `{color:red}…{color}`, ключи задач `ABC-123`, голые URL,
`\\` как перенос строки.

**Правило границ** — то, что чинит `user_name_id` и `C++`. Маркер открывается,
только если перед ним начало текста, пробел или один из `([{«"'`, и закрывается,
только если после него конец текста, пробел или знак препинания. Так ведёт себя
сама Jira. Следствия:

- `user_name_id` — `_` стоит после буквы, открывающим не считается, текст цел
- `C++`, `Java+Kotlin` — то же для `+`
- `5-10 дней` — то же для `-`
- `_курсив_` в обычной позиции работает как раньше

Неизвестный макрос `{что-то}текст{что-то}` отдаёт внутренний текст как обычный
текст, а не выбрасывает его.

### Шаг 3 — сборка HTML

Обход блоков и инлайновых узлов с выводом разметки. **Экранирование происходит
только здесь**, при выводе текстового содержимого, чистой функцией без обращения к
DOM:

```js
function escapeHtml(text) {
    return String(text)
        .replace(/&/g, '&amp;').replace(/</g, '&lt;').replace(/>/g, '&gt;')
        .replace(/"/g, '&quot;').replace(/'/g, '&#39;');
}
```

Нынешняя реализация через `document.createElement` не экранирует кавычки и требует
браузера — новая закрывает обе проблемы. Значения атрибутов (`href`, цвет)
экранируются той же функцией.

Классы и структура вывода сохраняются как сейчас, чтобы существующие стили в
`web/static/styles.css` продолжали работать: `jira-code`, `jira-table`,
`jira-panel`, `jira-panel-<тип>`, `jira-desc-link`, `jira-task-ref`, `jira-mention`.

## Поддерживаемая разметка

Заголовки `h1.`–`h6.`; абзацы; жирный, курсив, зачёркнутый, подчёркнутый, верхний и
нижний индекс; моноширинный `{{…}}`; ссылки `[текст|url]` и `[url]`; ключи задач;
голые URL; списки маркированные и нумерованные с вложенностью; таблицы с
заголовочными и обычными строками; `{code}` и `{noformat}`; `{quote}`; `{panel}` с
заголовком и без; `{color:…}`; горизонтальная линия `----`; перенос строки `\\`.

Осознанно не поддерживаются: картинки `!файл.png!`, `{toc}`, `{anchor}`,
`{status}`, `{expand}` и прочие макросы.

## Тестирование

`tests/js/wiki-parser.test.js`, запуск `node --test tests/js/`. Зависимостей не
требуется: `node --test` встроен, в системе Node v26.

`pytest` эти файлы не подхватывает — он собирает `test_*.py`. Питоновский набор
(285 тестов) остаётся зелёным и не пересекается с новым.

Тесты табличные, три группы:

1. **Не потерять работающее.** Все семь случаев из
   `tests/e2e/fixtures/wiki-samples.ts` — жирный, курсив, моноширинный,
   зачёркнутый, заголовок, блок кода, ссылка.
2. **Регрессии на найденные поломки.** Все восемь случаев из таблицы в начале
   документа, каждый отдельным тестом с явной проверкой того, что раньше ломалось:
   `user_name_id` цел; `href` ссылки равен исходному адресу; `C++` цел; панель
   имеет неповреждённые классы; нумерованный список даёт корректно вложенные теги;
   между `<li>` нет `<br>`; строки данных таблицы отрисованы, заголовок в `<th>`;
   содержимое блока кода дословно, без `<a>` и `<br>`.
3. **Правила и края.** Вложенные списки; таблица без заголовочной строки;
   незакрытый `{code}`; пустой ввод; текст без разметки; экранирование `<`, `>`,
   `&`, кавычек; неизвестный макрос отдаёт внутренний текст.

ADF-ветка после переноса в отдельный файл покрывается парой тестов на то, что
`parseJiraDescription` по-прежнему различает форматы: объект `type: 'doc'` идёт в
ADF, строка — в wiki.

Помимо автотестов — ручная проверка в браузере на составном описании, включающем
таблицу, вложенный список, блок кода и ссылку с подчёркиваниями в адресе.

## Риски

- **Что-то отрисуется иначе, чем раньше.** Часть нынешнего поведения возникает
  случайно, из-за наложения правил. Первая группа тестов фиксирует то, что
  работало осмысленно; остальное меняется намеренно.
- **Правило границ отвергнет разметку, к которой привыкли.** Например `-слово-`
  вплотную к цифрам больше не станет зачёркнутым. Это соответствует поведению
  Jira, но заметно для тех, кто полагался на прежнюю вольность.
- **Существующие стили рассчитаны на текущую структуру вывода.** Смягчается тем,
  что набор классов и вложенность сохраняются; проверяется глазами в браузере.
